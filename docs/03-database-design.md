# Database Design – PostgreSQL 17

Status: **APPROVED** (2026-11-06)

Conventions:
- Tables use `snake_case` (Prisma `@@map`). Primary keys are `INT GENERATED BY DEFAULT AS IDENTITY` (Prisma `autoincrement()`).
- Money is `NUMERIC(12,2)`, which goes up to ₹9,99,99,99,999.99. Quantities are `INT`.
- Business dates (issue, return, payment, invoice) are `DATE`, the calendar day in Asia/Kolkata. Audit timestamps are `TIMESTAMPTZ`.
- **Every foreign key is `ON DELETE RESTRICT`.** Nothing is cascade-deleted. Business records are deactivated, voided or cancelled, never deleted.
- Constraints Prisma cannot express (CHECK constraints, partial unique indexes) are added as hand-written SQL in the migration files.

---

## 1. Entity relationships

```
users ─┬─< (created_by / issued_by / received_by / voided_by on most tables)
       └─< audit_logs

categories ─< products ─┬─< product_units
                        └─< stock_movements >─ product_units (optional)

customers ─< rental_orders ─┬─< issues ─< issue_lines >─ products
                            │                  │      >─ product_units (serialised only)
                            │                  └─< return_lines >─ returns >─ rental_orders
                            ├─< invoices ─< invoice_lines
                            └─< payments

number_sequences   settings (single row)
```

Cardinality:
- 1 customer → many orders.
- 1 order → many issues (items added over time) → many issue lines.
- 1 order → many returns (partial returns).
- 1 issue line → many return lines (e.g. 10 props issued and returned 4 + 6).
- 1 order → at most **one active** invoice (cancelled ones remain).
- 1 order → many payments.

## 2. Tables

### customers
| Column | Type | Constraints |
|---|---|---|
| id | int PK | shown as the customer number |
| name | text | NOT NULL |
| phone | text | NOT NULL, indexed (not unique, since family members may share a number; a duplicate shows a warning in the UI) |
| alt_phone | text | null |
| address | text | null |
| id_proof_type | text | null (Aadhaar, Driving Licence, …) |
| id_proof_number | text | null |

Index: `lower(name)` for search.

### categories
`id`, `name` UNIQUE, `name_ml` null, `is_active`.

### products
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| category_id → categories | | NOT NULL |
| code | text | UNIQUE (short code, e.g. `GEN-5KVA`) |
| name / name_ml | text | name NOT NULL |
| tracking | enum `SERIALISED`,`QUANTITY` | NOT NULL, **cannot change after the first issue** (app rule) |
| daily_rate | numeric(12,2) | `CHECK (daily_rate > 0)` |
| qty_owned | int | `CHECK (qty_owned >= 0)` |
| qty_out | int | `CHECK (qty_out >= 0)` |
| qty_repair | int | `CHECK (qty_repair >= 0)` |
| description | text | null |
| is_active | bool | default true |
| created_at, updated_at | | |

Table CHECK: **`qty_out + qty_repair <= qty_owned`**, so overselling is impossible.
Derived value: `available = qty_owned − qty_out − qty_repair`.

The counters are maintained only by service transactions (see Architecture §6). Rate changes are written to `audit_logs` (old → new).

### product_units (serialised products only)
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| product_id → products | | NOT NULL |
| serial_no | text | NOT NULL, `UNIQUE (product_id, serial_no)` |
| status | enum `AVAILABLE`,`RENTED`,`UNDER_REPAIR`,`LOST`,`RETIRED` | NOT NULL |
| notes | text | null |

For a serialised product: `qty_owned` = units not LOST/RETIRED, `qty_out` = RENTED units and `qty_repair` = UNDER_REPAIR units (verified by the reconciliation test).

### stock_movements (ledger of every change to owned and repair stock)
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| product_id → products | | NOT NULL |
| unit_id → product_units | | null |
| type | enum `OPENING`,`PURCHASE`,`WRITE_OFF`,`SENT_TO_REPAIR`,`REPAIR_DONE`,`REPAIR_SCRAPPED`,`RETURN_DAMAGED`,`RETURN_LOST`,`CORRECTION` | |
| delta_owned | int | |
| delta_repair | int | `CHECK (delta_owned <> 0 OR delta_repair <> 0)` |
| return_line_id → return_lines | | null (set for RETURN_*) |
| reason | text | NOT NULL for WRITE_OFF / CORRECTION / REPAIR_SCRAPPED |
| created_by → users, created_at | | |

Issues and returns change `qty_out`; they are already recorded in issue and return lines, so they do not appear here.
Reconciliation: `qty_owned = Σ delta_owned`, `qty_repair = Σ delta_repair`, `qty_out = Σ active issued − Σ active returned`.

### rental_orders
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| order_no | text | UNIQUE (e.g. `ORD/2026-27/0001`) |
| customer_id → customers | | NOT NULL, indexed |
| status | enum `OPEN`,`CLOSED`,`CANCELLED` | indexed |
| site_address | text | null (where the equipment is being used; optional) |
| notes | text | null |
| opened_on | date | NOT NULL |
| closed_at | timestamptz | null |
| cancelled_by → users, cancelled_at, cancel_reason | | `CHECK (status <> 'CANCELLED' OR cancel_reason IS NOT NULL)` |
| created_by → users, created_at, updated_at | | |

An order can be cancelled only if it has no active issue lines and no active payments (app rule).
Numbering starts fresh at `0001` at go-live. For orders migrated from the paper register, the old register number goes in `notes`.

### issues
`id`, `order_id` → rental_orders, `issue_date DATE NOT NULL`, `is_backdated bool`, `notes`, `issued_by` → users, `created_at`.

### issue_lines
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| issue_id → issues | | NOT NULL |
| order_id → rental_orders | | NOT NULL (denormalised for fast order queries) |
| product_id → products | | NOT NULL |
| unit_id → product_units | | null, **required for SERIALISED products, forbidden for QUANTITY ones** (app rule) |
| quantity | int | `CHECK (quantity > 0)`, `CHECK (unit_id IS NULL OR quantity = 1)` |
| qty_returned | int | default 0, `CHECK (qty_returned BETWEEN 0 AND quantity)`, so over-return is impossible |
| daily_rate | numeric(12,2) | **rate snapshot**, `CHECK (daily_rate > 0)` |
| status | enum `ACTIVE`,`VOIDED` | |
| voided_by, voided_at, void_reason | | void allowed only when `qty_returned = 0` |

Partial unique index: `UNIQUE (unit_id) WHERE unit_id IS NOT NULL AND status = 'ACTIVE' AND qty_returned < quantity`. This guarantees **one physical unit can never be out on two rentals at once**.

### returns
`id`, `order_id` → rental_orders, `return_date DATE NOT NULL`, `is_backdated`, `notes`, `received_by` → users, `created_at`, `status ACTIVE|VOIDED`, void fields. A return can be voided by the admin only while the order has no active invoice, and voiding reverses its stock effects.

### return_lines
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| return_id → returns | | NOT NULL |
| issue_line_id → issue_lines | | NOT NULL, indexed |
| quantity | int | `CHECK (quantity > 0)` |
| condition | enum `GOOD`,`DAMAGED`,`LOST` | |
| days | int | `CHECK (days >= 1)` (calculated by the billing engine) |
| daily_rate | numeric(12,2) | copied from the issue line |
| rent_amount | numeric(12,2) | `CHECK (rent_amount = quantity * daily_rate * days)` |
| damage_amount | numeric(12,2) | default 0, `CHECK (damage_amount >= 0)` |
| damage_note | text | `CHECK ((condition = 'GOOD' AND damage_amount = 0) OR damage_note IS NOT NULL)` |

The rent CHECK makes the database itself verify the rent arithmetic. If a bug ever produced a wrong amount, the insert would fail instead of storing it.

### invoices
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| invoice_no | text | UNIQUE |
| order_id → rental_orders | | NOT NULL |
| status | enum `ISSUED`,`CANCELLED` | |
| invoice_date | date | |
| customer_name, customer_phone, customer_address | text | **snapshot** |
| rent_total, damage_total | numeric(12,2) | ≥ 0 |
| discount_amount | numeric(12,2) | default 0, `CHECK (discount_amount >= 0 AND discount_amount <= rent_total + damage_total)` |
| discount_reason | text | `CHECK (discount_amount = 0 OR discount_reason IS NOT NULL)` |
| total | numeric(12,2) | `CHECK (total = rent_total + damage_total − discount_amount)` |
| created_by, created_at, cancelled_by, cancelled_at, cancel_reason | | |

Partial unique index: `UNIQUE (order_id) WHERE status = 'ISSUED'`, so an order has **at most one live invoice**.

### invoice_lines (immutable snapshot)
`id`, `invoice_id`, `sort_order`, `product_name`, `product_name_ml`, `serial_no`, `quantity`, `issue_date`, `return_date`, `days`, `daily_rate`, `rent_amount`, `condition`, `damage_amount`, `damage_note`.

### payments
| Column | Type | Constraints |
|---|---|---|
| id | int PK | |
| receipt_no | text | UNIQUE (`RCP/…` for money in, `RFD/…` for refunds) |
| order_id → rental_orders | | NOT NULL, indexed |
| customer_id → customers | | NOT NULL (denormalised for customer outstanding reports) |
| type | enum `ADVANCE`,`PAYMENT`,`REFUND` | ADVANCE = before the invoice, PAYMENT = after it (set automatically) |
| mode | enum `CASH`,`UPI`,`BANK_TRANSFER`,`CHEQUE` | |
| amount | numeric(12,2) | `CHECK (amount > 0)` |
| payment_date | date | NOT NULL; always the entry date (Asia/Kolkata), never backdated |
| reference | text | null (UPI ref, cheque number) |
| notes | text | null |
| status | enum `ACTIVE`,`VOIDED` | void fields + reason (admin only) |
| received_by → users, created_at | | |

**Order balance (computed, never stored):**
`balance = live_invoice.total − Σ active ADVANCE/PAYMENT + Σ active REFUND`
(Before the invoice exists, the statement uses accrued rent in place of `invoice.total`.)

### number_sequences
`doc_type` (`ORDER`,`INVOICE`,`RECEIPT`,`REFUND`), `fiscal_year` (e.g. `2026-27`), `next_value int`. PK `(doc_type, fiscal_year)`. Incremented with `UPDATE … RETURNING` inside the business transaction, which keeps numbering gap-free.

### settings (single row)
`id` with `CHECK (id = 1)`, `business_name`, `business_name_ml`, `address`, `address_ml`, `phones`, `email`, `order_prefix`, `invoice_prefix`, `receipt_prefix`, `refund_prefix`, `invoice_terms`, `invoice_terms_ml`, `logo_path`, `print_paper_width_mm` (int, default 80, `CHECK (print_paper_width_mm IN (58, 80))`; A4 may be added later), `updated_by`, `updated_at`.

### audit_logs
`id bigint`, `actor_id` → users, `action` (e.g. `ISSUE_CREATE`, `PAYMENT_VOID`, `RATE_CHANGE`, `BACKDATE`), `entity`, `entity_id`, `summary jsonb` (before/after of the key fields), `reason`, `created_at`. Indexes: `(entity, entity_id)`, `created_at`. The app only ever inserts into this table, never updates or deletes.

## 3. Key indexes (besides PKs/UNIQUEs)
- `rental_orders (customer_id, status)`, `rental_orders (status, opened_on)`
- `issue_lines (order_id)`, `issue_lines (product_id) WHERE status='ACTIVE' AND qty_returned < quantity` (items currently out)
- `return_lines (issue_line_id)`
- `payments (order_id)`, `payments (customer_id)`, `payments (payment_date)` (collection reports)
- `invoices (invoice_date)`
- `customers (phone)`, `customers (lower(name))`

## 4. Seed data
- First admin user (username and password from env vars; must change the password on first login).
- The `settings` row with the business name "Sree Krishna Motors" and default prefixes `ORD`, `INV`, `RCP`, `RFD`.
- **Development only:** sample categories, products (both tracking types, with units), one staff user and a few customers. The production seed creates only the admin and the settings row.

## 5. Backup & recovery
- Nightly `pg_dump -Fc` (custom format, compressed), with 30 daily + 12 monthly copies retained.
- A copy is stored off the machine. **The destination is decided together with hosting** (options: Google Drive folder or USB on the shop PC; rclone to cloud storage on the VPS).
- Restore uses `pg_restore` into a fresh database, scripted. **A restore drill is part of handover.**
